一、完成的使用者流程

冒險入口的「世界首領」與營地入口的「首領精華」進入現有主戰鬥單一浮窗，共用世界首領／精華兌換／材料回收三分頁。沿用金屬控件、透明背景、至少44px操作區及原頁尾導覽。320、390與1280寬度驗收可操作，長內容在浮窗內捲動。

世界首領顯示目前首領、HP、場次期限、自己的真實傷害與次數、目前攻擊窗口、角色HP／MP、倒地期限及已保存戰果。active、settling、killed、fled、vanished狀態分別呈現，不把HP0直接當作已完成獎勵。確認頁明列目標、技能、五次施放、補魔選項與倒地10分鐘規則；取消／Back回來源按鈕。

精華頁讀取角色實際精華、遺物碎片及原目錄。原七種兌換不改價：
- 5精華 → 5洗屬性捲。
- 5精華 → 4武器卷軸。
- 5精華 → 4防具卷軸。
- 80精華 → 1祝福武器卷軸。
- 80精華 → 1祝福防具卷軸。
- 5精華 → 1遺物碎片。
- 30遺物碎片 → 1件依原職業／階級規則產生的隨機遺物。

材料回收列出當前全數持有的mat_3／mat_4及數量，原費率為12／16精華。確認綁定當時精確數量，送出前或提交時數量不同即拒絕舊確認，要求讀取實際餘額後重新確認。

帳號每日精華獎勵顯示台灣日界、已用／上限4／剩餘次數。只有實際有貢獻的擊殺計入；同帳號不同角色在同場只領一次，物品歸原結算選出的貢獻角色。達上限仍可攻擊，不把帳號上限當成禁戰條件。

二、新API與原權威的界線

新增boss/scene及boss/receipt為SELECT-only；新增boss/attack-scoped及boss/exchange-scoped處理主浮窗操作。App與內部Service均驗證body.realmId、X-Realm-Id、帳號身分及selectedCharacterId；呼叫者提供的tgId或namespace不能更換權威身分。

scene與receipt不經withPlayer、analytics或原currentBoss副作用路徑，不清理過期、不推進、不結算、不補發、不寫outbox。凍結世界仍可讀，寫入維持原phase／fence限制。舊boss/current相關行為保持，不把舊副作用查詢加入READS。

scopedBossEnv在原寫入batch內驗證帳號與當前選角，涵蓋withPlayer失敗動作仍可能產生的idle settlement、重試、Boss結算及outbox。純SELECT batch不加入寫入。攻擊與擊殺結算仍沿用原來兩筆交易：若攻擊已提交、隨後切角使結算被擋，合法攻擊與原守護憑證仍保留，首領可以維持HP0／settling，等待原權威路徑處理；新查詢不假裝完成或代為修復。

未新增migration，未改正式DB、Secrets、旗標或部署設定。原3分鐘攻擊窗口、30分鐘場次、10分鐘倒地與精華價格／產量不縮短或重設。

三、攻擊未知結果與兌換收據

攻擊原子鍵為bossId＋characterId＋win，與塔印的requestId模式不同。新scoped攻擊要求非負整數expectedWin，固定本次request時間，跨窗口在expire／withPlayer任何寫入前拒絕。讀取原攻擊結果時保留bossId／win，即使found:false也不丟失原tuple。

原attack資料只存damage與created_at。因此attack-row恢復只能呈現已有證據，不虛構crit、反擊、HP／MP、擊殺或獎勵。未知攻擊在重開／切角／跨窗後保留原窗口，查證不重送。新窗口必須另外明確確認新攻擊；沒有跨窗自動補打。

兌換在原消耗與產出同一persist batch寫入scoped-only的版本化零額ledger收據。收據綁定requestId、完整offer／材料數量signature、實際cost與完整結果，並核對原currency、item及equipment ledgers。同ID／相同內容回原結果；同ID換內容409。遺物找回原裝備ID，不再抽一次；裝備之後已售出也不因此重擲。

舊版、破損或部分ledger不能冒充成功，也不能解除pending後重新花費。只有有效的found:false且recoveryAllowed:true，使用者再次明示確認後，才能原ID／原body恢復未送達兌換。取消、Back、刷新、關窗、回前景及收據查詢均不自動POST。

材料回收除工作狀態比對外，另在SQL batch以實際扣除後兩種材料均為0作提交guard，涵蓋沒有增加character revision的並行材料增量。本次真實競態驗收先增加1件mat_3，舊確認被整筆回滾；重新確認實際3件mat_3＋3件mat_4後，一次換得84精華。

四、共用session與焦點

pending依realm／帳號／角色隔離；A→B→A的晚成功、晚409或已提交但回覆遺失都不能套用至新的context。revision floor保留，不讓舊快照退回新狀態。B不能看到A的pending，回A仍以原ID／tuple查證。

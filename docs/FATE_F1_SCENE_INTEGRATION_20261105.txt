三、權威邊界與防重
App 與 Service 均新增 fate/scene、fate/receipt、fate/action-scoped。前二者只 SELECT，不經有副作用的舊 me／state／daily／social、withPlayer、step、sweep 或行為統計路徑。後者從可信路由固定 namespace，驗證 header／body realm、驗證帳號及 captured selectedCharacterId。
每個原 batch／run 均重新檢查角色與 realm fence，涵蓋前置、主交易與後置；不是只在入口做一次檢查。原服務只加可選可信 hooks，不新增 migration，不更改原公開故事引擎。
scene 以 fate 欄位返回，避免和 shared session 的 Atlas scene 混淆；server readSequence、前後 domain／actor 再核對、最多一次重取及明確 snapshot_changed，配合 client epoch、最新請求序、同 life revision floor 拒絕晚回覆。domain hash 用於等值比對，不拿 hash 作時間順序。
五種操作：start、choice、keep、gift-claim、gift-open。start 只准 random／country／showSign／socialInvite=false；choice 使用精確 lifeId、index、answer；claim 使用排序唯一 expectedMilestones；open 精確 giftId。F1 拒生日與 profile 欄位。
typed ledger「命運場景操作收據」delta=0，與原操作的最後權威 batch 同批提交，保留原 intent、原 immutable result、scope、成本與核對證據。claim 的 completed count／既有 milestone／預期里程碑以 SQL CAS 再驗。開匣後歷史 claim 仍可驗，人生往後推進後原 start／choice 仍可查。
原服務可能先有合法前置提交；找不到 typed receipt 不代表前面全部沒有寫入。若存在部分權威操作，recoveryAllowed=false，不能以「查無」自動重送。
UI 在寫入前保存並讀回完整 canonical pending，保留 false／0／null 的語義；不確定結果、切角、重掛或刷新不換 ID、不自動再送。明確核對原收據；僅在服務確認可恢復且使用者明示時，才用原 ID 與完整原 body 重試。壞 storage 原文保留，不以 cache 覆寫。
已驗證不可變收據的確認與新網路回覆的新鮮度分開：後續純刷新推進 now／revision，不會讓原收據無法確認；確認原結果也不把目前 scene 倒退。gift-open 原第五 RNG 參數不動，可信 options 使用第六參數。
